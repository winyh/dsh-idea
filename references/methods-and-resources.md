# Idea Discovery 方法与资源

本文件是 `idea-discovery` skill 的参考卡，不要求用户先读完。使用时按问题选择方法，避免框架堆叠。

默认顺序是：外部市场/公开来源 → 需求信号 → 机会主题 → 候选解法 → 验证实验。本地文件用于保存外部研究快照、补充访谈和离线复盘，不是产品定位的核心边界。

## 方法速查

### 人本设计 / Design Thinking

适合：问题空间不清楚、需要理解用户生活/工作情境、需要从观察中获得新机会。

常用动作：定义受众 → 观察/访谈 → 综合洞察 → How Might We → 发散 → 原型 → 反馈迭代。

提醒：人本设计不是“先画漂亮方案”；在定义问题时保留多个解释，避免把第一种解决方案当成需求本身。

### Jobs To Be Done（JTBD）

适合：用户会用多种产品完成同一任务，或团队把“用户画像”写得很宽泛。

常用问法：发生了什么触发事件？用户想推进什么进展？现在怎么完成？为什么不满意？在什么条件下会换方案？成功如何衡量？

提醒：Job 是用户想完成的进展，不是“想要一个 App”；用最近一次具体经历追问，不要只问未来愿望。

### 持续发现 / Continuous Discovery

适合：产品团队需要持续产生并筛选机会，而不是季度末集中做一次研究。

常用动作：明确结果 → 持续访谈/观察 → 记录机会 → 构建机会解法树 → 以小实验测试假设。

提醒：每周接触用户只是节奏，不是目标；关键在于研究结果能否改变优先级或方案。

### Opportunity Solution Tree（OST）

适合：需求、功能和解决方案混在一起，团队需要建立共同决策结构。

结构：目标结果 → 机会/未满足需要 → 多个候选解法 → 验证实验。

提醒：机会不是功能名；一个机会应允许多个解法，树上保留被放弃的分支并记录原因。

### Design Sprint

适合：团队需要在有限时间内对一个高风险挑战快速对齐、做原型并拿到用户反馈。

常用动作：理解/定义 → 独立草图 → 决策 → 原型 → 用户测试。

提醒：Sprint 不是一次性“定案会”，应把结果写成学习和后续实验；没有真实用户测试就只是内部工作坊。

### Lean Startup / 假设驱动实验

适合：已有方向但不知道需求、方案、分发或商业模式中哪条假设最危险。

常用动作：写假设 → 找最小可行学习方式 → Build-Measure-Learn → 根据阈值继续、调整或停止。

提醒：MVP 的目标是最大化学习，不是把完整产品缩小；能用人工服务、原型或预售验证时，不要先写全栈系统。

### Value Proposition Canvas / Business Model Canvas

适合：需要比较用户价值、竞争替代、渠道、成本、收入和关键资源。

常用动作：先写 Customer Jobs / Pains / Gains，再连接产品服务、痛点缓解和收益创造；最后补齐商业模式假设。

提醒：Canvas 是假设地图，不是商业模式已被证明；把事实、估计和未知分别标注。

### Outcome-Driven Innovation（ODI）

适合：已经知道用户的大致 Job，但需要找出哪些结果最重要、最未被满足。

常用动作：把 Job 拆成可观察的期望结果 → 询问结果的重要性和满意度 → 找出高重要、低满意的结果 → 围绕结果设计机会。

提醒：结果要写成“减少完成任务所需的时间/错误/不确定性”，不要写成“增加一个按钮”；问卷分数只能帮助排序，仍需回到真实行为和付费/迁移证据。

### The Mom Test / 非引导式访谈

适合：用户访谈容易变成“你觉得这个想法怎么样”，团队需要减少礼貌性赞同和假设性回答。

常用问法：请讲最近一次发生这件事的经过；你当时先做了什么；现在怎么解决；花了多少时间、钱或人力；谁参与决策；为什么没有换方案。

提醒：多问过去发生的具体事件，少问未来愿望；“我会用”“听起来不错”是弱证据，真实迁移、预算、时间承诺和付费才是更强证据。

### Assumption Mapping / Riskiest Assumption Test

适合：候选 idea 很多，但不知道哪一条假设最可能让项目失败。

常用动作：列出用户、问题、方案、触达、支付、技术和合规假设 → 按重要性 × 认知程度排序 → 先测试“最重要且最不了解”的假设。

提醒：不要一开始测试最容易的页面偏好；优先验证问题是否真实、用户是否可触达、是否愿意付出真实承诺。

### Switching / 关键事件访谈

适合：用户已经从一个方案换到另一个方案，或正在考虑替代现有工具。

常用动作：还原触发事件 → 记录拉力、推力、惯性和焦虑 → 追问比较、试用、迁移和最终决策 → 找到“为什么是现在”。

提醒：不要只研究满意用户；流失、弃用、迁移和人工 workaround 往往包含更强的机会信号。

## Idea 信号库

## 如何挖掘用户需求

### 一条需求记录至少要回答

```text
谁：具体角色、组织、市场和购买关系
何时：触发事件、频率和为什么是现在
要完成什么：功能 Job、情绪 Job、社会 Job 或期望结果
现在怎么做：竞品、人工、表格、脚本、外包、群聊或放弃
付出什么：时间、金钱、错误、风险、焦虑、机会成本
哪里不满意：现有替代方案的具体缺口
证据是什么：原话、行为、交易、迁移、重复出现、来源和日期
下一步怎么证伪：最小实验、样本、周期、成功/失败阈值
```

### 访谈问题模板

1. “请讲最近一次你遇到这个问题的完整过程。”
2. “是什么事情触发了它？你当时先做了什么，之后又做了什么？”
3. “你现在用什么方式解决？哪些步骤最麻烦或最容易出错？”
4. “你试过哪些工具、人工方法或替代方案？为什么没有继续用？”
5. “这件事最近一次造成了什么时间、金钱、风险或机会损失？”
6. “谁会受到影响、谁会决定、谁会付费？”
7. “如果现在不解决，会发生什么？什么变化会让你必须马上处理？”

避免直接问：“你会不会用这个产品？”“你愿不愿意付费？”“你希望有哪些功能？”这些问题可以作为补充，但不能替代对过去行为的追问。

### 需求证据强弱梯度

从强到弱可大致按以下顺序判断：已经付费/续费或迁移 → 正在用 workaround、外包或多个工具拼接 → 反复发生且有明确代价 → 公开社区中多人描述相似场景 → 搜索、点赞、收藏、评论热度 → 单个人的未来愿望。

这不是机械打分规则。单个高价值客户的强证据，可能比大量低意向点赞更有价值；关键是记录情境、代价、重复性和可触达性。

### 直接问题信号

- 用户反复问同一个问题，且现有答案无法解决下一步。
- 用户在不同工具之间复制粘贴、重复录入、人工对账或维护脆弱脚本。
- 用户花钱买多个工具、顾问、外包或培训来拼出一条工作流。
- 用户因为流程复杂而拖延、放弃、出错、返工或无法交付结果。

### 公开市场信号

- 应用商店或 SaaS 评论中的重复负面场景和迁移原因。
- GitHub issues、论坛和问答中的未解决问题、 workaround 和高频追问。
- 招聘描述里反复出现的流程、合规、数据整理或运营工作。
- 竞品的定价、限制、集成缺口、更新日志和用户迁移讨论。
- 搜索趋势、内容评论、社区成员增长、供应链/技术成本/政策变化。

### 信号判断

对每条信号记录：来源、日期、对象、场景、行为、代价、频率、可重复性、可信度和下一步验证。把“很多人讨论”与“很多人会付费”分开。

## 外部机会雷达

这是对公开痛点检索类产品的部分吸收：借鉴“关键词 + 多维筛选 + 排序 + 保存视图 + 导出”的研究入口，并把它放在外部市场机会发现的第一层；不把它当成完整的 idea 生成器。

### 推荐筛选维度

- 主题/关键词：行业、技术、任务或行为变化。
- 市场/地域/语言：目标市场、地区、语言和监管边界。
- 痛点场景：例如创业管理、内容运营、交付协作、学习、就业或合规。
- 目标用户：角色、组织规模、经验水平、使用频率和购买角色。
- 来源：访谈、客服、社区、应用评论、GitHub issue、搜索趋势、竞品反馈。
- 时间：最新、近 30 天、近 90 天或长期反复出现。
- 信号强度：具体行为、重复提及、现有 workaround、投入成本、明确求助或付费迹象。

### 推荐排序

不要只做“最热”排序。至少提供：

1. 最新：发现新出现的问题和变化。
2. 重复：发现跨用户、跨来源反复出现的问题。
3. 痛苦：发现损失、风险或阻塞明显的问题。
4. 可验证：发现来源清晰、用户可触达、适合快速测试的问题。

### 痛点卡片字段

```text
痛点标题：
一句话问题：
目标用户：
具体场景：
原始证据摘要：
来源链接：
出现日期：
重复提及数：
当前 workaround：
时间/金钱/风险代价：
信号强度：弱 / 中 / 强
置信度：低 / 中 / 高
需要补充的证据：
对应机会主题：
下一步验证：
```

### 使用边界

- 公开信号只能帮助发现问题，不能直接证明需求、市场规模或支付意愿。
- 不抓取或展示不必要的个人信息；优先保留去标识化摘要和来源链接。
- 没有可核验来源时标记为“灵感”，不写成“用户普遍需要”。
- 先聚类为机会主题，再生成多个解法；避免把单条抱怨直接变成一个功能。
- 如果要持续追踪，保存的是研究视图和更新时间，不是静态的“机会排行榜”。
- 外部页面优先记录发布日期和抓取时间；页面被截断、拒绝访问或需要登录时，明确标记限制。

### 资源使用方法

| 资源 | 先看什么 | 推荐搜索动作 | 主要证据类型 | 误用风险 |
| --- | --- | --- | --- | --- |
| Product Hunt | 同一类别的产品、评论区、用户追问、maker 回复和发布后的反馈 | 类别/任务词 + “alternative”“missing”“hard”“wish” | 解决方案地图、定位、早期采用者语言 | 发布热度不等于留存或支付意愿；不要只复制热门产品 |
| TrustMRR | 类别、价格、MRR/增长、技术栈、营销渠道、最近上架项目 | 类别 × 价格区间 × 增长/收入 × tech stack | 已商业化的市场存在、价格锚点、分发方式 | 上架项目有选择偏差；核对收入口径和条款，不复制业务或数据 |
| Reddit | 具体 subreddit、原帖上下文、评论中的 workaround 和替代产品 | `how do I`、`any alternative`、`frustrated`、`manually`、`wish`、`too expensive` | 原生问题语言、场景、替代方案 | 社区不代表整个市场；遵守版规，不把观察变成骚扰或营销 |
| G2 | 1–3 星评论、Pros/Cons、替代产品、实施和迁移经历 | 类别/竞品 + “cons”“alternative”“missing”“integration” | B2B 购买后反馈、缺口和迁移原因 | 评论有平台和样本偏差，不能把评分当成完整市场需求 |
| GitHub | 重复 issue、upvotes、标签、复现步骤、维护者是否回应 | 项目/生态 + `issue`、`feature request`、`workaround`、`alternative` | 技术痛点、可复现缺口、生态需求 | 开源用户不等于付费用户；需求可能受项目路线限制 |
| Google Trends | 趋势方向、季节性、地区和相关查询 | 比较 3–5 个同义词/替代词，限定地区和时间 | 关注变化、市场教育和关键词语言 | 是相对兴趣，不是销量、支付意愿或市场规模 |

Product Hunt 更适合回答“最近出现了哪些解法、谁在尝试、用户怎么评价”；TrustMRR 更适合回答“哪些细分市场已经有人做、怎么定价、是否出现了商业化和分发信号”。二者都需要和用户问题证据结合：前者偏解决方案与早期市场，后者偏商业存在与价格参考，不能单独证明需求。

## 书籍关键词

- *The Mom Test*：如何问出行为事实，减少引导式访谈。
- *Continuous Discovery Habits*：把用户接触、机会树和小实验变成团队习惯。
- *Sprint*：在短周期内把高风险问题推进到原型和测试。
- *The Lean Startup*：以验证学习和最小实验降低不确定性。
- *Value Proposition Design*：把用户任务、痛点、收益与价值主张连接起来。
- *Inspired*：产品发现、产品团队和产品决策的实践视角。
